## Корень репозитория и публикация

- Корнем проекта считается папка, содержащая `.git`, `AGENTS.md`, `README.md` и `index.html`.
- Перед изменением или публикацией проверь корень командой `git rev-parse --show-toplevel`.
- Для публикации клиента используй только корень репозитория и ветку `main`; каталог `yandex` содержит архив функции, но не является корнем Git-работы.

## Назначение и архитектура

Проект — статическое PWA «Мой нутрициолог» для GitHub Pages.

- `index.html` — основной интерфейс и клиентская логика.
- `firebase-client.js` — Firebase Auth/Firestore и локальный fallback.
- `firestore.rules` — правила доступа Firestore по UID пользователя.
- `manifest.webmanifest`, `service-worker.js`, `pwa.js`, `notifications.js`, `icons/` — PWA и локальные уведомления.
- `worker/` — Cloudflare Worker, общие серверные модули ИИ; `yandex/` — адаптер Cloud Functions.
- `README.md` — документация по развёртыванию и архитектурным решениям.

## Обязательные правила безопасности

- Никогда не помещай `OPENAI_API_KEY` или другие приватные ключи/токены в Git, HTML, Firebase web config, `wrangler.toml`, логи или документацию.
- AI API вызывается только через серверный шлюз (Yandex Cloud Functions или Cloudflare Worker). Браузер не должен получать API-ключ.
- Firebase Web config является публичной клиентской конфигурацией; не путай её с серверными секретами.
- Запись пользовательских данных в Firestore выполняется клиентским Firebase SDK под текущим пользователем и защищается `firestore.rules`.
- Worker не должен получать Firebase service account и не должен напрямую записывать пользовательский дневник.
- ИИ может только предложить блюдо (`proposedMeal`). Сохранять его разрешается исключительно после явного подтверждения пользователя кнопкой «Добавить».
- Не ослабляй CORS до `*` без явного решения пользователя.
- Не добавляй обходы региональных ограничений провайдеров.

## Правила изменения проекта

- Каждая публикация обязана повышать версию интерфейса: обновляй `APP_VERSION` и дату релиза в `app.js`, версию/дату в `PROJECT_STATUS.md`, а после коммита создавай и отправляй соответствующий Git-тег `vX.Y.Z`.
- Сохраняй возможность статического размещения интерфейса на GitHub Pages.
- Не вводи backend-зависимость для функций, которые уже безопасно работают локально, без необходимости.
- Сохраняй гостевой/local fallback при недоступном или ненастроенном Firebase, если задача явно не требует другого поведения.
- Не активируй Google Authentication автоматически. Это делается только после настройки провайдера и support email в Firebase Console.
- Фото блюда по умолчанию используется только для одного запроса и не сохраняется. Не добавляй постоянное хранение фото без отдельной задачи и правил Firebase Storage.
- Голосовой ввод сейчас должен оставаться браузерным (Web Speech API / Speech Synthesis), если пользователь отдельно не попросил серверный realtime/audio режим.
- Не меняй публичный контракт Worker `{ advice, proposedMeal }` без одновременной проверки клиента и документации.
- При добавлении ИИ-провайдера сохраняй единый контракт и держи его секреты только в серверном хранилище (Yandex Lockbox / Cloudflare Worker secrets).

## Проверка перед завершением задачи

Минимально проверь:

1. `git diff` — нет случайных изменений и секретов.
2. Ссылки/импорты указывают на существующие файлы.
3. Клиент не содержит приватных API-ключей.
4. Сценарий предложения блюда по-прежнему требует подтверждения перед записью.
5. Если менялись PWA-файлы — проверь пути к manifest/service worker/icons и отсутствие ненужного кэширования секретных/пользовательских данных.
6. Если менялся Worker — проверь POST/OPTIONS, валидацию входа, CORS и обработку ошибок.
7. Если менялась структура/поведение/развёртывание — актуализируй `README.md`.

## PROJECT_STATUS.md — перенос контекста между ПК

После каждой существенной законченной задачи обнови `PROJECT_STATUS.md`.

Записывай только полезное для следующей сессии:

- что реально реализовано;
- какие файлы существенно изменены;
- принятые архитектурные решения;
- что требует внешней настройки;
- известные ошибки/несоответствия;
- текущую задачу и следующий разумный шаг.

Не превращай файл в журнал чата и не записывай туда секреты, ключи, пароли или персональные данные.

Перед `git push` убедись, что `PROJECT_STATUS.md` соответствует фактическому состоянию репозитория.
