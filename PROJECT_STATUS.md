## Локальные данные и голосовой ввод Wear OS (2026-10-10)

В исходниках Wear 0.2.4/versionCode 6: LocalNutritionStore хранит UID/guest-разделённые записи дневника/воду/вес/черновик и устойчивую очередь. Диск записывается через IO, серверное подтверждение не блокирует форму. Стабильный ID еды предотвращает дубль при повторной отправке; версия операции защищает новое изменение от позднего ack. Кэш объединяет серверные документы по ID с ожидающими локальными; запоздалое чтение не затирает локальное изменение. Старую неразделённую воду не импортируем в аккаунт, потому что владельца установить невозможно; первая успешная облачная загрузка восстанавливает значение. Параллельные чтения ограничены 4 секундами, начальная сводка отображается локально сразу. При отказе сервера очередь сохраняется/показывает предупреждение; повтор — запуск/возврат приложения или карточка калорий. При смене UID собственная очередь не отправляется под новым аккаунтом; гостевые записи не мигрируют автоматически. Конфликты нескольких устройств по-прежнему last-write-wins.

FoodScreen использует RecognizerIntent системной русской диктовки, клавиатурный fallback, сохраняет текстовый черновик. FoodAi отправляет только текст и Firebase ID token существующему шлюзу d4evergfv4q48plpsdbu, без новых серверных ключей/аудио/изменения CORS или контракта. Расчёт проходит строгую проверку массы/БЖУ и показывается перед отдельным «Добавить в дневник» за сегодня с выбором приёма пищи. ИИ/диктовка сами не записывают дневник; нерассчитанный офлайн-текст остаётся черновиком. ИИ требует сети/аккаунта и расходует текущую квоту; офлайн-распознавание зависит от установленного системного провайдера. Приложение не обещает отправку собственного обработчика очереди при закрытом процессе.

Финальные assembleDebug и 9 JVM-тестов LocalNutritionStoreTest прошли (0 ошибок): перезапуск, UID/guest, поздний ack, overlay без дубля, устаревшие чтения, черновик, смена дня, валидация, несколько предложений/уточнение. ## Назначение приложения

«Мой нутрициолог» — статическое PWA в Yandex Object Storage:

`Yandex Object Storage → Yandex Cloud Functions → Blackroute → модель`

Клиент хранит дневник питания, воду, вес, профиль и личную базу продуктов через Firebase. При недоступном Firebase пользователь может явно продолжить работу в гостевом режиме с локальным `localStorage`.

## Исправленные ошибки

- **Дата по UTC.** `dataDateKey()`/`dateKeyFor()` использовали `toISOString()`, поэтому в Москве сутки дневника переключались в 03:00, а не в полночь: приём пищи в 01:00 попадал в предыдущий день. Теперь `js/date.js` и `localDateKey()` в `firebase-client.js` считают локальную дату. Зафиксировано тестом `tests/core.test.mjs`.
- **Инъекция разметки.** Название блюда из ответа ИИ и из личной базы подставлялось в `innerHTML` (`renderPlan`, окно предложения блюда). Теперь названия вставляются через `textContent`.
- **Кнопка фото в форме блюда.** `app.js` перезаписывал обработчик из `photo-picker.js` своим `window.confirm`, поэтому в форме не было выбора «Фото / Галерея», хотя это заявлено в документации. Теперь обе кнопки открывают один и тот же выбор.
- **Утечка слушателя окна входа.** Обработчик `nutrition-auth-status` оставался после закрытия окна и продолжал обращаться к удалённой разметке.
- **Подмена `toast`.** Расчёт ИИ подменял глобальную функцию `toast`, перехватывая текст ошибки. Теперь ошибка передаётся явно.
- **Потеря БЖУ при подтверждении блюда от ИИ.** `window.addProposedMeal` сохранял только название, калории и приём пищи, теряя белки, жиры, углеводы и порцию.
- **Удаление записи.** Значения БЖУ парсились регуляркой из текста строки. Теперь они лежат в `dataset` строки.
- **Пустой дневник.** После удаления последней записи карточка приёма пищи удалялась, а подсказка «Записей пока нет» не возвращалась — экран дневника оставался полностью пустым. Теперь пустая подсказка восстанавливается.
- **Пересчёт после фото.** При переносе распознанного блюда в форму сбрасывалась база оценки (`recognizedManualMealEstimate = null`), поэтому после изменения порции БЖУ и калории не пересчитывались. Теперь база сохраняется, и ввод порции пересчитывает значения пропорционально.
- **Сетка формы блюда.** После выноса разметки в `index.html` остались лишние колонки: под кнопку фото, которая теперь живёт внутри поля названия (пустая полоса справа от порции), и третья колонка в строке БЖУ из двух полей. Раскладка приведена к виду «название → порция и калории → БЖУ в три колонки».
- **Календарь дневника.** Вместо задуманной кнопки 📅 в шапке появилось видимое поле даты шириной 44 px, в которое не помещалась дата («04.»). Кнопка со скрытым полем даты восстановлена: `showPicker()` не работает для `display:none`, поэтому поле скрыто через `opacity:0` и размер 1 px.
- **Порядок инициализации.** `initMealForm` пересобирает кнопку расчёта, поэтому состояние доступности ИИ рассчитывается после неё.

## Реализовано

- Google Authentication и вход по email/password с обработкой медленной сети, повторным подключением и явным гостевым режимом. Для email-аккаунтов доступны письма восстановления и подтверждения адреса; вошедший через Google пользователь может привязать пароль к тому же email без потери UID.
- UID-разделение данных в Firestore; кэшируется только профиль, токены не сохраняются вручную.
- При временных ошибках Firestore изменения профиля, дневника, воды, веса и личной базы продуктов попадают в UID-разделённую локальную очередь. Они видимы сразу, автоматически отправляются после восстановления сети/входа, а профиль показывает число ожидающих изменений. ## Wear OS: интерфейс и вход с телефона (2026-10-09, локальные изменения)

- Главный экран сохраняет кнопки «Вес: N кг» (последняя запись не позднее сегодня) и «Вода: N / 8». Вода открывает отдельный экран с заголовком, −/+, количеством по центру, сохранением и отменой; выход без сохранения не меняет значение. Вес вводится на отдельном экране.
- В `MainActivity.kt` используется lifecycle-aware coroutine scope; сетевые вызовы сопряжения идут на IO. Вода обновляется локально сразу, вода/вес ждут подтверждения Firestore не более 5 секунд, затем сообщают об ожидании сети. Физические часы пользователь считает медленными; устранение всех лагов не подтверждено.
- Подготовлены `wear-auth/` (отдельный Node/Firebase Admin сервис), `js/wear-pairing.js`, `js/wear-config.js` и `PhoneSignIn.kt`: одноразовый 5-минутный код, проверка токена телефона, отдельное подтверждение, секрет устройства, однократная выдача custom token. Пароль и refresh token телефона не передаются; ИИ-шлюз и дневник сервисом не используются. Отдельный компаньон не нужен, используется PWA телефона, но часы должны иметь интернет.
- Сервис НЕ развёрнут: нужны отдельные runtime identity, изолированная Firestore база/IAM, TTL и публичный HTTPS endpoint. Endpoint в исходниках пуст. Проверки in-memory не заменяют реальную Firebase/IAM проверку. Публикации PWA и установки на физические часы в этой задаче не было; перед публикацией повысить версию/тег по правилам проекта.
- Проверки: assembleDebug успешна (APK 0.2.0), эмулятор открывает отдельный экран воды и отменяет черновик без изменения сохранённого количества. 12 серверных тестов, браузерная проверка двухэтапного подключения/смены UID/гостя/отмены, 23 существующих браузерных сценария и 24 выбранных модульных теста прошли. Production-модули импортируются с firebase-admin 14.5.0; npm audit — 0 уязвимостей. Кэш оболочки v60 включает только публичные модули подключения, не auth API.
