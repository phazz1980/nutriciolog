# Мой нутрициолог

Это статический PWA, опубликованный через Cloudflare Pages. ИИ-консультация выполняется Cloudflare Worker: ключ провайдера остаётся в секрете Worker и никогда не загружается в браузер.

## Публикация в Yandex Object Storage

Workflow `.github/workflows/deploy-yandex.yml` автоматически публикует статические файлы в бакет `nutriciolog-x20` при push в `main`. Учётные данные находятся в GitHub Actions secrets `YC_ACCESS_KEY_ID` и `YC_SECRET_ACCESS_KEY`. Адрес сайта: https://nutriciolog-x20.website.yandexcloud.net/. Worker публикуется отдельно.

При публикации v0.2.3 (25 сентября 2026) Yandex возвращает `AccessDenied` на `PutObject`: подготовка файлов исправлена, но нужно проверить права сервисного аккаунта, ключи и политику бакета. Основной сайт Cloudflare Pages обновлён успешно.

## Cloudflare Pages

1. Создайте GitHub-репозиторий и загрузите в его корень `index.html`, `README.md` и папку `worker`.
2. В Cloudflare откройте **Workers & Pages → Create application → Pages → Import an existing Git repository** и выберите репозиторий.
3. Для этого статического проекта задайте ветку `main`, build command `exit 0` и build output directory `.`. Cloudflare выдаст адрес на `pages.dev`.

## Защищённый сервер советов

1. Создайте Worker в Cloudflare и загрузите содержимое папки `worker` (или выполните публикацию через Wrangler у себя).
2. В настройках Worker добавьте секрет с именем `BLACKROUTE_API_KEY`. Его значением служит ключ Blackroute. Не добавляйте его в `index.html`, `wrangler.toml`, GitHub или сообщения.
3. В `worker/src/index.js` явно разрешены origins `https://nutriciolog.pages.dev` и `https://nutriciolog-x20.website.yandexcloud.net`. Для других origins Worker не выдаёт разрешение CORS.
4. Worker опубликован по адресу `https://my-nutritionist-advice.340052.workers.dev/api/advice`; это значение уже задано в `index.html`.
5. ИИ доступен любому пользователю, вошедшему через Firebase Authentication. При необходимости ограничение по email можно вернуть отдельной доработкой.

## Ограничения

ИИ отвечает только на общие вопросы о питании и здоровом образе жизни. На вопросы вне этих тем он кратко предложит вернуться к питанию или ЗОЖ. Он не диагностирует заболевания, не назначает лечение и не заменяет врача.

## Firebase: аккаунт и данные

Firebase хранит данные приложения и вход пользователя. Cloudflare Worker остаётся только шлюзом к ИИ; у него нет доступа к Firestore и ему не нужен Firebase service account.

Worker проверяет подпись Firebase ID token через официальный Google JWK endpoint и кэширует публичные ключи по `Cache-Control`. Приватные ключи Firebase или service account ему не передаются.

1. В Firebase Console создайте проект и добавьте Web App. Скопируйте **публичную** конфигурацию Web App в `firebase-client.js`, заменив все `YOUR_...`. Это не секрет и не содержит ключ OpenAI.
2. В **Authentication → Sign-in method → Google** включите провайдер и укажите support email. В **Authorized domains** добавьте `nutriciolog.pages.dev`. Вход через Google нужен для синхронизации и является обязательным для доступа к ИИ.
3. В **Firestore Database** создайте базу и опубликуйте правила из `firestore.rules`. Они разрешают доступ только к документам текущего пользователя: `users/{uid}/...`.
4. Данные организованы так: `users/{uid}/profile/main`, `foodDiary/{дата-uuid}`, `waterLogs/{YYYY-MM-DD}`, `weightEntries/{YYYY-MM-DD}` и личная база продуктов `products/{normalizedName}`. Профиль, вода, ручные блюда, вес и продукты записываются клиентским Firebase SDK после входа; без входа или конфигурации Firebase они безопасно остаются локально в браузере. Вода загружается только для текущей даты и автоматически начинает новый день с нуля. После входа гостевой профиль не подставляется вместо профиля аккаунта.

На странице «Профиль» можно изменить имя, возраст, рост, текущий и целевой вес, цель и дневную норму. Из Google-аккаунта при входе подставляется только доступное базовое имя; параметры здоровья Google не запрашиваются и заполняются пользователем. На главной странице приветствие меняется по местному времени, а при наличии фотографии Google-аккаунта она отображается вместо стандартной ветки. Сохранение профиля использует тот же Firebase-документ `profile/main` или локальное хранилище в гостевом режиме.

При медленном интернете приложение отдельно показывает загрузку Firebase и восстановление сессии. До первого ответа Auth отсутствие пользователя не считается выходом из аккаунта: чтение, запись и получение токена ждут до 15 секунд, после чего предлагают повторить действие. Тайм-аут не отменяет восстановление сессии и не переводит запись автоматически в гостевое хранилище. При недоступном Firebase в профиле можно явно выбрать «Продолжить как гость»; гостевые данные остаются отдельно от данных аккаунта.

После сбоя загрузки Auth/Firestore доступно повторное подключение, в том числе при возвращении сети. При сбое базового модуля Firebase требуется явная перезагрузка страницы: базовый модуль должен оставаться общим для всех SDK. Вход через Google открывается только по нажатию пользователя; повторные нажатия используют уже начатую попытку. Ошибки сети, закрытого или заблокированного окна показываются с пояснениями. Если окно входа остаётся белым во встроенном браузере, откройте тот же сайт в Safari/Chrome и повторите вход при устойчивом соединении. Сбой обновления токена не вызывает ложное окно «Нужна авторизация»; введённые поля блюда сохраняются при неудачной попытке входа без перезагрузки страницы.

Внутренний диалог входа оформлен в мятно-зелёном стиле приложения. Ожидание и ошибки показываются в отдельном блоке; «Позже» или Escape закрывает окно и возвращает фокус. Внешняя страница выбора Google-аккаунта остаётся стандартной страницей Google.

Профиль аккаунта кэшируется в `localStorage` отдельно по UID. После восстановления сессии Firebase сохранённые имя и параметры отображаются сразу, без ожидания Firestore; серверное чтение обновляет профиль в фоне. При сетевой ошибке остаётся последняя сохранённая копия. Успешное редактирование обновляет кэш, а выход или смена аккаунта удаляет кэш предыдущего пользователя. Кэш содержит только поля профиля, не токены, и не предоставляет доступ к ИИ. При первом входе кэш ещё отсутствует. Сессию входа сохраняет сам [Firebase Auth](https://firebase.google.com/docs/auth/web/auth-state-persistence), если браузер разрешает локальное хранение.

Кнопки расчёта ИИ, распознавания в ручной форме и отправки совета приглушаются при отсутствии сети/входа, восстановлении сессии, ошибке токена или обнаруженном сбое сервиса. Рядом отображается причина; действия остаются доступными для входа или повторной попытки, чтобы интерфейс не блокировался навсегда. Успешный повтор восстанавливает обычный цвет. Недоступность провайдера определяется по результату запроса, без фоновых платных обращений к ИИ.

## Как ИИ добавляет блюдо

Если пользователь явно просит добавить блюдо, Worker может вернуть только структурированное предложение: название, калории и приём пищи. Он не выполняет операций с базой. Интерфейс показывает предложение и сохраняет его в дневник только после явного нажатия пользователя «Добавить» — через Firebase client SDK и правила Firestore. Для ручного блюда и предложения ИИ пользователь выбирает дату: сегодня или завтра. Дневник начинается без демонстрационных записей и объединяет продукты одного приёма пищи в общую карточку; сохранённые записи за сегодня загружаются при открытии приложения. Любую отдельную запись, включая перекус, можно удалить кнопкой ×. БЖУ вводятся пользователем для ручного блюда или приходят из подтверждённой карточки продукта ИИ; главная сводка складывает эти значения, а цели БЖУ рассчитывает из дневной калорийности в профиле (30% белки, 30% жиры, 40% углеводы).

В дневнике рядом с названием дня есть кнопка календаря 📅. Через неё можно выбрать любую прошлую дату, сегодня или завтра и просмотреть сохранённые приёмы пищи, порции, БЖУ и сумму калорий прямо в дневнике. Просмотр работает и в Firebase, и в локальном режиме и не изменяет записи выбранной даты.

В ручной форме можно указать название и вес порции, затем нажать «Рассчитать с ИИ». После входа через Google приложение отправляет только эти данные в защищённый Worker и подставляет ориентировочные калории и БЖУ в форму. Если ИИ запросил уточнение, вопрос и ответ с дополнительными ингредиентами сохраняются в личной базе после нажатия «Сохранить»; при следующем вводе того же блюда показывается напоминание. Блюдо по-прежнему сохраняется только после отдельного нажатия «Сохранить».

Если пользователь запускает такой расчёт без входа, приложение показывает окно с пояснением. Нажатие «Перейти к входу» по явному действию пользователя открывает стандартное окно Google Authentication; при недоступности Firebase пользователь попадает в профиль.

`BLACKROUTE_API_KEY` задаётся только как Cloudflare Worker secret. Его никогда не следует помещать в Firebase, GitHub Pages, исходный код или конфигурацию Firebase.

## Личная база продуктов и карточки ИИ

Когда пользователь просит разобрать или добавить еду по продуктам, ИИ возвращает отдельные предложения с массой, калориями и БЖУ. Интерфейс сверяет название с личной базой текущего пользователя по нормализованному имени и, если запись уже существует, использует сохранённые значения. У каждой карточки есть выбор приёма пищи, даты «Сегодня / Завтра» и отдельная кнопка «Добавить»: только этот клик записывает один продукт в дневник. Новый подтверждённый продукт одновременно сохраняется в `users/{uid}/products/{normalizedName}` для следующих предложений; Worker не читает и не записывает эту базу. Правила Firestore уже разрешают доступ к любым подколлекциям только при совпадении `request.auth.uid` и `userId`, поэтому продукты одного аккаунта не доступны другому.

## Провайдер ИИ

По умолчанию Worker использует Blackroute с моделью `gemini-3-flash-preview` для текста и `gemini-2.5-flash` для запросов с фото. Обе модели запрашиваются в JSON-режиме; модель для фото поддерживает распознавание блюда. Установите переменную Worker `AI_PROVIDER=blackroute`, необязательные переменные `BLACKROUTE_MODEL=gemini-3-flash-preview` и `BLACKROUTE_VISION_MODEL=gemini-2.5-flash`, а также секрет `BLACKROUTE_API_KEY`. Веб-интерфейс получает единый ответ `{ advice, proposedMeal }` и не зависит от конкретной модели или поставщика. Временная строка отладки показывает статус запроса и HTTP-статус Worker, но не выводит ключи, токены или данные аккаунта.

Выбранные модели Blackroute поддерживают JSON-режим. Worker запрашивает структурированный ответ с лимитом 1 000 токенов и дополнительно проверяет его перед передачей приложению; при ошибке Blackroute безопасно сообщает о проблеме с ключом, моделью, лимитом или временной недоступностью без раскрытия секрета. Если модель всё же вернёт ответ в неподходящем формате, Worker один раз автоматически повторит запрос с требованием вернуть только JSON и тем же лимитом. Если повтор тоже не удался, на вкладке «Совет» появится раскрываемый блок «Показать ответ ИИ для диагностики»: в нём доступны фрагменты обеих попыток общей длиной до 4 000 символов и кнопка копирования. Эти фрагменты показываются только авторизованному пользователю, не сохраняются и маскируют строки вида `Bearer …` и `sk-…`.

Если Worker сообщает, что не видит ключ Blackroute, создайте в настройках Worker именно Secret с именем `BLACKROUTE_API_KEY`, а не обычную переменную.

Для безопасной диагностики доступен `GET /api/health`: он показывает версию Worker, активного провайдера, текстовую и фото-модель, а также наличие runtime-секрета, но никогда не возвращает сам ключ.

Структура `worker/src/providers/` — точка расширения. Новый адаптер (например, для GigaChat или YandexGPT) должен реализовать `advise(message)` и вернуть тот же объект; его выбор добавляется в `providers/index.js`. Ключ альтернативного провайдера должен храниться только в секрете Worker. Не добавляйте ключи или выбор провайдера в GitHub Pages или Firebase.

Подключайте Blackroute только в соответствии с его условиями использования. Этот проект не реализует обход региональных ограничений.

## Фото блюда

На вкладке «Совет» кнопка камеры открывает тот же выбор «Фото / Галерея», что и ручное добавление блюда. «Фото» запрашивает камеру, «Галерея» — выбор изображения или файла; отмена сохраняет текущий черновик. Можно выбрать или снять фото JPEG, PNG или WebP до 4 МБ. После распознавания в карточке каждого продукта можно скорректировать вес порции в граммах рядом с выбором приёма пищи и даты; приложение пропорционально пересчитает калории и БЖУ перед сохранением. Перед отправкой фото видно только локально, его можно удалить. По умолчанию фото передаётся в Worker лишь для одного запроса совета и не сохраняется в Firebase. Оценки калорий и макронутриентов по фото приблизительны и не являются медицинской рекомендацией.

В форме ручного добавления блюда рядом с названием есть кнопка камеры. Она распознаёт выбранное фото и заполняет название, вес, калории и БЖУ, но не сохраняет запись автоматически: пользователь всё ещё выбирает приём пищи и дату, проверяет значения и нажимает «Сохранить».

Если ответ ИИ не прошёл проверку формата, форма ручного распознавания показывает раскрываемый диагностический фрагмент ответа и кнопку копирования. Он доступен только авторизованному пользователю и не сохраняется.

Провайдеры сообщают возможность `supportsVision`. Если выбранный адаптер не поддерживает изображения (например, будущий DeepSeek/Qwen-адаптер без vision), Worker вернёт понятную просьбу описать блюдо текстом. Контракт ответа и подтверждение добавления блюда остаются прежними.

Если позднее потребуется хранить фотографии, используйте Firebase Storage только с путями пользователя, например `users/{uid}/meal-photos/{photoId}`. Добавьте правила Storage, аналогичные Firestore: `request.auth != null && request.auth.uid == userId` для read/write по этому пути, и проверяйте допустимый MIME-тип/размер. Не передавайте изображение от Worker в Storage и не используйте service account: пользовательский Firebase SDK и правила должны оставаться единственным путём записи. Для текущей версии сохранять фото не требуется.

## Голосовой режим

Голосовой режим использует встроенное распознавание речи Web Speech API: он распознаёт русскую речь и вставляет результат в поле вопроса. Нажмите 🎙, чтобы начать; во время записи кнопка становится ■ и отменяет ввод. Озвучивание ответов в браузере отключено. Поддержка, качество распознавания и запрос разрешения к микрофону зависят от браузера и устройства; при недоступности используйте текстовый ввод.

Голосовой режим не требует ключа, нового backend или сохранения аудио. В будущем его можно заменить серверным real-time/audio-streaming адаптером выбранного провайдера, сохранив тот же безопасный пользовательский поток подтверждения блюда. Эта версия не подключает и не развёртывает платный streaming-сервис.

## Установка PWA и офлайн-режим

Для установки нужны HTTPS и опубликованные `manifest.webmanifest`, `service-worker.js`, `pwa.js` и папка `icons` рядом с `index.html`. GitHub Pages уже работает по HTTPS и поддерживает относительные пути проекта. Установка остаётся доступной через стандартное меню браузера: «Установить приложение» или «Добавить на главный экран».

Service Worker кэширует только перечисленные файлы оболочки приложения и только успешные ответы. Если оболочка уже есть в кэше, при задержке сети дольше 4 секунд используется сохранённая копия; успешный ответ позже обновляет кэш. API, Firebase SDK, токены и пользовательские данные этим кэшем не обслуживаются. Гостевые локальные функции доступны офлайн, но Firebase-синхронизация, вход и ИИ требуют сети; офлайн-синхронизация облачных данных не заявляется.

## Проверка авторизации при нестабильной сети

`tests/auth-network.cjs` запускает браузерные проверки через Playwright с подменёнными Firebase SDK: задержка восстановления сессии, запрет случайной гостевой записи, гостевой режим, повтор загрузки SDK, ошибки и повтор popup, задержка/ошибка токена, сохранение полей блюда. Отдельно проверяются тайм-аут кэша оболочки и исключение API/SDK/POST из service worker. Для запуска нужен установленный `playwright` и браузер: `node tests/auth-network.cjs`. Можно задать `PLAYWRIGHT_MODULE` (путь к установленному пакету) и `BROWSER_CHANNEL=msedge` для установленного Edge. Также проверяются кэш профиля между перезагрузками, фоновое обновление, выход/смена аккаунта, поздние ответы, недоступное локальное хранилище, состояние кнопок ИИ и оба выбора источника фото. Настоящий вход Google и ограничения iOS проверяются отдельно на устройстве.

## Мобильные формы

Поля форм используют шрифт 16 px и сжимаемые колонки, чтобы избежать увеличения при фокусе и выхода полей за границы экрана на iPhone. Длинные формы прокручиваются внутри окна; при появлении клавиатуры высота и положение окна следуют Visual Viewport, с CSS-fallback для браузеров без этого API. Масштабирование жестом остаётся доступным.

Перед ИИ-расчётом обязательны название и положительное значение порции. Если поле не заполнено, рядом с ним появляется подсказка и фокус переходит в это поле; запрос к ИИ не отправляется. Число в названии блюда не заменяет заполнение поля «Порция».

При открытии ручной формы поля белков, жиров и углеводов не содержат числовых примеров. Они заполняются пользователем или результатом расчёта ИИ.
