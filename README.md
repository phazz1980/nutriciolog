## Ручной ввод калорий и БЖУ

В общих исходниках Web/Android рядом с порцией расположен переключатель «На всё блюдо / На 100 г». Ниже одним рядом идут калории и необязательные белки, жиры и углеводы. Переключатель задаёт смысл введённых чисел, сами числа при переключении не меняются. В режиме «На 100 г» при сохранении калории и БЖУ умножаются на вес порции / 100; в дневник и личную базу записываются итоги всей порции. Для этого режима нужен вес в граммах, а не количество штук. Калории обязательны; пустые БЖУ допускаются, но текущий числовой контракт хранения по-прежнему учитывает их как 0 (отдельного признака неизвестных БЖУ пока нет).

ИИ, фото, JSON и выбор личного продукта заполняют значения на всё блюдо и переключают форму в этот режим. Ручная правка питания отключает прежний автоматический пересчёт оценки по порции. Сохранение остаётся явным, кнопкой «Сохранить». Правка опубликована и установлена на Pixel 8 в релизе 0.4.5 от 12.10.2026.

## Ввод блюда из JSON

Вставьте JSON в поле названия блюда или в поле «Совет»: он автоматически заполнит форму, без запроса серверному ИИ. Кнопка «Спросить у другого ИИ» под полем ввода открывает подсказку с кнопкой копирования скрытого промпта: сначала напишите блюдо, затем вставьте промпт без изменений. Без указанного веса ИИ оценит обычную порцию. Формат:

    {"title":"Салат","portion":250,"calories":350,"protein":25,"fat":10,"carbs":40}

Порция — в граммах, БЖУ и калории — на всю порцию; числовые поля без единиц. calories можно пропустить: вычисляется по формуле 4 × белки + 9 × жиры + 4 × углеводы. Поддерживается JSON в Markdown-блоке. Проверьте оценку и выберите приём пищи: в дневник блюдо попадёт только по «Сохранить». Некорректный JSON не меняет черновик.


Переключатель темы (2026-10-11): в профиле три видимых варианта «Системная / Светлая / Тёмная» вместо выпадающего списка. При первом запуске без сохранённого выбора активна системная тема; прежний выбор сохраняется. Доступен с клавиатуры, синхронизация нативной панели сохранена. ## Ограничения

ИИ отвечает только на общие вопросы о питании и здоровом образе жизни. На вопросы вне этих тем он кратко предложит вернуться к питанию или ЗОЖ. Он не диагностирует заболевания, не назначает лечение и не заменяет врача.

### Месячный лимит ИИ

Сервер ограничивает каждый Firebase UID **1000 запросами в календарный месяц UTC**. Текст, расчёт БЖУ и фото используют один общий счётчик на всех устройствах. Один принятый запрос списывается перед обращением к модели; ошибки провайдера и таймауты не возвращают попытку. Внутренний повтор для исправления формата ответа входит в эту попытку. Ошибки входа и валидации не расходуют квоту. При неопределённом сетевом результате списание не повторяется автоматически и не откатывается: оно могло уже сохраниться на сервере.

Остаток и дату обновления показывает карточка «Запросы к ИИ» в профиле. Кнопка «Обновить», вход и открытие профиля запрашивают состояние без списания; ответы ИИ также обновляют остаток. Это лимит запросов приложения, не баланс токенов или денег Blackroute. После исчерпания сервер возвращает HTTP 429 с `code: "quota_exceeded"`; при недоступном или ненастроенном хранилище — HTTP 503 с `code: "quota_unavailable"`, без обращения к модели. Ручной дневник и гостевой режим не зависят от этой проверки.

Счётчики хранятся отдельно от дневника в YDB Document API, атомарно по ключу `(uid, period)`. Клиент не имеет доступа к таблице и не задаёт UID или величину лимита. Ответ `{ advice, proposedMeal, proposedProducts }` дополнен полем `quota: { unit, limit, used, remaining, period, resetsAt }`; авторизованный `POST { "action": "usage" }` возвращает `{ quota, costs }`. Ответы имеют `Cache-Control: no-store`; квоты не записываются в localStorage или кэш PWA.

Перед публикацией шлюза обязательно настройте YDB по [инструкции](yandex/README.md#месячная-квота-запросов). Резервный Cloudflare не должен использовать старый неограниченный шлюз: новая версия без серверного `AI_QUOTA_STORE` останавливает ИИ с 503. Старую публичную функцию/Worker с тем же ключом нужно отключить либо обновить перед включением лимита.

Проверки: `node --test tests/core.test.mjs tests/yandex.test.mjs tests/photo-upload.test.mjs tests/quota.test.mjs` и `node tests/auth-network.cjs`.

## Firebase: аккаунт и данные

Firebase хранит данные приложения и вход пользователя. Yandex Cloud Functions остаётся только шлюзом к ИИ; у него нет доступа к Firestore и ему не нужен Firebase service account.

Worker проверяет подпись Firebase ID token через официальный Google JWK endpoint и кэширует публичные ключи по `Cache-Control`. Приватные ключи Firebase или service account ему не передаются.

1. В Firebase Console создайте проект и добавьте Web App. Скопируйте **публичную** конфигурацию Web App в `firebase-client.js`, заменив все `YOUR_...`. Это не секрет и не содержит ключ OpenAI.
2. В **Authentication → Sign-in method** включите **Email/Password**. В **Authorized domains** добавьте `nutriciolog.pages.dev` и другие опубликованные домены приложения; для Android-контейнера Capacitor также добавьте `localhost` (без схемы). Вход по email/password нужен для синхронизации и является обязательным для доступа к ИИ.
3. В **Firestore Database** создайте базу и опубликуйте правила из `firestore.rules`. Они разрешают доступ только к документам текущего пользователя: `users/{uid}/...`.
4. Данные организованы так: `users/{uid}/profile/main`, `foodDiary/{дата-uuid}`, `waterLogs/{YYYY-MM-DD}`, `weightEntries/{YYYY-MM-DD}` и личная база продуктов `products/{normalizedName}`. Профиль, вода, ручные блюда, вес и продукты записываются клиентским Firebase SDK после входа; без входа или конфигурации Firebase они безопасно остаются локально в браузере. Вода загружается только для текущей даты и автоматически начинает новый день с нуля. После входа гостевой профиль не подставляется вместо профиля аккаунта.

На странице «Профиль» можно изменить имя, возраст, рост, текущий и целевой вес, цель и дневную норму. Параметры здоровья заполняются пользователем; фото профиля не используется. Сохранение профиля использует тот же Firebase-документ `profile/main` или локальное хранилище в гостевом режиме.

Firebase Auth использует явную постоянную browser persistence: восстановленная сессия остаётся в хранилище самого Firebase, а приложение не копирует и не кэширует пользователей, credentials или ID-токены. Пользователь может войти по email/password, создать аккаунт или запросить письмо для восстановления пароля; после регистрации Firebase автоматически отправляет письмо подтверждения email. До подтверждения в профиле доступны повторная отправка и проверка статуса. Письма и пароль обрабатываются Firebase Auth и не передаются Worker. Service Worker заранее и только как публичный код кэширует Firebase App/Auth/Firestore SDK, поэтому при повторном запуске не нужно заново ждать их загрузку из `gstatic`; это не делает вход или синхронизацию доступными без сети.

После удаления Google-входа не отключайте провайдера Google в Firebase Console, пока пользователи, которые входили только через него, не перенесут аккаунты на email/password отдельной управляемой процедурой. Новые вход и регистрация в приложении выполняются только по email/password.

Для диагностики каждый ответ ИИ выводится в консоль браузера как `[ИИ] Ответ Worker`: доступны HTTP-статус и тело ответа для советника, расчёта и распознавания блюд. Запрос, Firebase ID token, заголовок `Authorization` и фото в консоль не выводятся.

При медленном интернете приложение отдельно показывает загрузку Firebase и восстановление сессии. До первого ответа Auth отсутствие пользователя не считается выходом из аккаунта: чтение, запись и получение токена ждут до 15 секунд, после чего предлагают повторить действие. Тайм-аут не отменяет восстановление сессии и не переводит запись автоматически в гостевое хранилище. При недоступном Firebase в профиле можно явно выбрать «Продолжить как гость»; гостевые данные остаются отдельно от данных аккаунта.

`firestore.rules` дополнительно проверяет допустимые поля, типы и диапазоны для профиля, дневника, воды, веса, продуктов и плана; UID-проверка остаётся обязательной. После следующей публикации примените этот файл в **Firestore Database → Rules → Publish**. До публикации в консоли действуют прежние правила, поэтому изменение репозитория само по себе защиту не усиливает.

После сбоя загрузки Auth/Firestore доступно повторное подключение, в том числе при возвращении сети. При сбое базового модуля Firebase требуется явная перезагрузка страницы: базовый модуль должен оставаться общим для всех SDK. Для email-входа и регистрации показываются понятные сообщения об ошибках, а «Восстановить пароль» отправляет письмо на введённый адрес. Сбой обновления токена не вызывает ложное окно «Нужна авторизация»; введённые поля блюда сохраняются при неудачной попытке входа без перезагрузки страницы.

Внутренний диалог входа оформлен в мятно-зелёном стиле приложения. Он ведёт к форме email/password в профиле; «Позже» или Escape закрывает окно и возвращает фокус.

Профиль аккаунта кэшируется в `localStorage` отдельно по UID. После восстановления сессии Firebase сохранённые имя и параметры отображаются сразу, без ожидания Firestore; серверное чтение обновляет профиль в фоне. При сетевой ошибке остаётся последняя сохранённая копия. Успешное редактирование обновляет кэш, а выход или смена аккаунта удаляет кэш предыдущего пользователя. Кэш содержит только поля профиля, не токены, и не предоставляет доступ к ИИ. При первом входе кэш ещё отсутствует. Сессию входа сохраняет сам [Firebase Auth](https://firebase.google.com/docs/auth/web/auth-state-persistence), если браузер разрешает локальное хранение.

При временной ошибке Firestore изменения профиля, дневника, воды, веса и личной базы продуктов помещаются в локальную очередь, изолированную по UID. Они остаются видимыми в приложении и автоматически отправляются после возврата сети или восстановления входа; строка в профиле показывает количество ожидающих изменений. Очередь не содержит Firebase-токенов и не применяется к ошибкам прав доступа или некорректным данным: такие ошибки не маскируются и требуют исправления. В Android-контейнере чтение дневника при обрыве потокового соединения Firestore дополнительно повторяется через Firebase Firestore Lite — обычный HTTPS-канал, полезный в сетях с VPN или фильтрацией. При одновременном редактировании воды на разных устройствах по-прежнему действует последнее сохранение — полноценное объединение счётчиков является отдельной задачей.

Кнопки расчёта ИИ, распознавания в ручной форме и отправки совета приглушаются при отсутствии сети/входа, восстановлении сессии, ошибке токена или обнаруженном сбое сервиса. Рядом отображается причина; действия остаются доступными для входа или повторной попытки, чтобы интерфейс не блокировался навсегда. Успешный повтор восстанавливает обычный цвет. Недоступность провайдера определяется по результату запроса, без фоновых платных обращений к ИИ.

## Как ИИ добавляет блюдо

Если пользователь явно просит добавить блюдо, Worker может вернуть только структурированное предложение: название, калории и приём пищи. Он не выполняет операций с базой. Интерфейс показывает предложение и сохраняет его в дневник только после явного нажатия пользователя «Добавить» — через Firebase client SDK и правила Firestore. Для ручного блюда и предложения ИИ пользователь выбирает дату: сегодня или завтра. Дневник начинается без демонстрационных записей и объединяет продукты одного приёма пищи в общую карточку; сохранённые записи за сегодня загружаются при открытии приложения. Любую отдельную запись, включая перекус, можно удалить кнопкой ×. БЖУ вводятся пользователем для ручного блюда или приходят из подтверждённой карточки продукта ИИ; главная сводка складывает эти значения, а цели БЖУ рассчитывает из дневной калорийности в профиле (30% белки, 30% жиры, 40% углеводы).

В дневнике рядом с названием дня есть кнопка календаря 📅. Через неё можно выбрать любую прошлую дату, сегодня или завтра и просмотреть сохранённые приёмы пищи, порции, БЖУ и сумму калорий прямо в дневнике. Просмотр работает и в Firebase, и в локальном режиме и не изменяет записи выбранной даты.

В ручной форме можно указать название и вес порции, затем нажать «Рассчитать с ИИ». Пока Worker обрабатывает запрос, форма показывает таймлайн отправки, анализа и получения результата с отсчётом до 60-секундного таймаута. После входа в аккаунт приложение отправляет только эти данные в защищённый Worker и подставляет ориентировочные калории и БЖУ в форму. Если ИИ запросил уточнение, вопрос и ответ с дополнительными ингредиентами сохраняются в личной базе после нажатия «Сохранить»; при следующем вводе того же блюда показывается напоминание. Блюдо по-прежнему сохраняется только после отдельного нажатия «Сохранить».

Если пользователь запускает такой расчёт без входа, приложение показывает окно с пояснением. Нажатие «Войти по email» открывает профиль с формой авторизации; при недоступности Firebase пользователь может продолжить как гость.

`BLACKROUTE_API_KEY` подключается к Cloud Functions через Yandex Lockbox (для резервного Cloudflare Worker — через Worker secret). Его никогда не следует помещать в Firebase, GitHub Pages, исходный код или конфигурацию Firebase.

## Личная база продуктов и карточки ИИ

Когда пользователь просит разобрать или добавить еду по продуктам, ИИ возвращает отдельные предложения с массой, калориями и БЖУ. Интерфейс сверяет название с личной базой текущего пользователя по нормализованному имени и, если запись уже существует, использует сохранённые значения. У каждой карточки есть выбор приёма пищи, даты «Сегодня / Завтра» и отдельная кнопка «Добавить»: только этот клик записывает один продукт в дневник. Новый подтверждённый продукт одновременно сохраняется в `users/{uid}/products/{normalizedName}` для следующих предложений. В списке личной базы его можно удалить после подтверждения; удаляется только этот документ базы, не записи дневника. Worker не читает и не записывает эту базу. Правила Firestore уже разрешают доступ к любым подколлекциям только при совпадении `request.auth.uid` и `userId`, поэтому продукты одного аккаунта не доступны другому.

## Провайдер ИИ

По умолчанию Worker использует Blackroute с моделью `deepseek-v3.2-maas` для текста и `gemini-2.5-flash` для запросов с фото. Обе модели запрашиваются в JSON-режиме; модель для фото поддерживает распознавание блюда. Установите переменную Worker `AI_PROVIDER=blackroute`, необязательные переменные `BLACKROUTE_MODEL=deepseek-v3.2-maas` и `BLACKROUTE_VISION_MODEL=gemini-2.5-flash`, а также секрет `BLACKROUTE_API_KEY`. Веб-интерфейс получает единый ответ `{ advice, proposedMeal }` и не зависит от конкретной модели или поставщика. Временная строка отладки показывает статус запроса и HTTP-статус Worker, но не выводит ключи, токены или данные аккаунта.

Выбранные модели Blackroute поддерживают JSON-режим. Worker запрашивает структурированный ответ с лимитом 1 000 токенов и дополнительно проверяет его перед передачей приложению; при ошибке Blackroute безопасно сообщает о проблеме с ключом, моделью, лимитом или временной недоступностью без раскрытия секрета. Если модель всё же вернёт ответ в неподходящем формате, Worker один раз автоматически повторит запрос с требованием вернуть только JSON и тем же лимитом. Если повтор тоже не удался, на вкладке «Совет» появится раскрываемый блок «Показать ответ ИИ для диагностики»: в нём доступны фрагменты обеих попыток общей длиной до 4 000 символов и кнопка копирования. Эти фрагменты показываются только авторизованному пользователю, не сохраняются и маскируют строки вида `Bearer …` и `sk-…`.

Если Worker сообщает, что не видит ключ Blackroute, создайте в настройках Worker именно Secret с именем `BLACKROUTE_API_KEY`, а не обычную переменную.

Для безопасной диагностики доступен `GET /api/health`: он показывает версию Worker, активного провайдера, текстовую и фото-модель, а также наличие runtime-секрета, но никогда не возвращает сам ключ. Текущая версия Worker в исходниках — `0.1.20` (задаётся константой `WORKER_VERSION` в `worker/src/index.js`).

Структура `worker/src/providers/` — точка расширения. Новый адаптер (например, для GigaChat или YandexGPT) должен реализовать `advise(message)` и вернуть тот же объект; его выбор добавляется в `providers/index.js`. Ключ альтернативного провайдера должен храниться только в секрете Worker. Не добавляйте ключи или выбор провайдера в GitHub Pages или Firebase.

Подключайте Blackroute только в соответствии с его условиями использования. Этот проект не реализует обход региональных ограничений.

## Фото блюда

На вкладке «Совет» кнопка камеры открывает тот же выбор «Фото / Галерея», что и ручное добавление блюда. «Фото» запрашивает камеру, «Галерея» — выбор изображения или файла; отмена сохраняет текущий черновик. Можно выбрать или снять фото JPEG, PNG или WebP до 4 МБ. После распознавания результат переносится в стандартное окно «Добавить блюдо»: там можно изменить название, порцию, БЖУ, приём пищи и дату, а затем вручную нажать «Сохранить». Перед отправкой фото видно только локально, его можно удалить. По умолчанию фото передаётся в Worker лишь для одного запроса совета и не сохраняется в Firebase. Оценки калорий и макронутриентов по фото приблизительны и не являются медицинской рекомендацией.

В форме ручного добавления блюда рядом с названием есть кнопка камеры. Она открывает тот же выбор «Фото / Галерея», что и вкладка «Совет». После распознавания кнопка «Перенести в форму» заполняет название, вес, калории и БЖУ, но не сохраняет запись автоматически: пользователь всё ещё выбирает приём пищи и дату, проверяет значения и отдельно нажимает «Сохранить». Само окно результата фото не записывает данные в дневник. Если на упаковке уверенно читается бренд, он включается в название как «Продукт — бренд»; неразборчивый бренд ИИ не должен угадывать.

Если ответ ИИ не прошёл проверку формата, форма ручного распознавания показывает раскрываемый диагностический фрагмент ответа и кнопку копирования. Он доступен только авторизованному пользователю и не сохраняется.

Провайдеры сообщают возможность `supportsVision`. Если выбранный адаптер не поддерживает изображения (например, будущий DeepSeek/Qwen-адаптер без vision), Worker вернёт понятную просьбу описать блюдо текстом. Контракт ответа и подтверждение добавления блюда остаются прежними.

Если позднее потребуется хранить фотографии, используйте Firebase Storage только с путями пользователя, например `users/{uid}/meal-photos/{photoId}`. Добавьте правила Storage, аналогичные Firestore: `request.auth != null && request.auth.uid == userId` для read/write по этому пути, и проверяйте допустимый MIME-тип/размер. Не передавайте изображение от Worker в Storage и не используйте service account: пользовательский Firebase SDK и правила должны оставаться единственным путём записи. Для текущей версии сохранять фото не требуется.

## Голосовой режим

Голосовой режим использует встроенное распознавание речи Web Speech API: он распознаёт русскую речь и вставляет результат в поле вопроса. Нажмите 🎙, чтобы начать; во время записи кнопка становится ■ и отменяет ввод. Озвучивание ответов в браузере отключено. Поддержка, качество распознавания и запрос разрешения к микрофону зависят от браузера и устройства; при недоступности используйте текстовый ввод.

Голосовой режим не требует ключа, нового backend или сохранения аудио. В будущем его можно заменить серверным real-time/audio-streaming адаптером выбранного провайдера, сохранив тот же безопасный пользовательский поток подтверждения блюда. Эта версия не подключает и не развёртывает платный streaming-сервис.

## Установка PWA и офлайн-режим

Для установки нужны HTTPS и опубликованные `manifest.webmanifest`, `service-worker.js`, `pwa.js` и папка `icons` рядом с `index.html`. GitHub Pages уже работает по HTTPS и поддерживает относительные пути проекта. Установка остаётся доступной через стандартное меню браузера: «Установить приложение» или «Добавить на главный экран».

Service Worker кэширует только перечисленные файлы оболочки приложения и только успешные ответы, а также публичные файлы Firebase App/Auth/Firestore SDK. Если оболочка уже есть в кэше, при задержке сети дольше 4 секунд используется сохранённая копия; успешный ответ позже обновляет кэш. API, Firebase persistence, токены и пользовательские данные этим кэшем не обслуживаются. Гостевые локальные функции доступны офлайн, но Firebase-синхронизация, вход и ИИ требуют сети; офлайн-синхронизация облачных данных не заявляется.

## Android (в подготовке)

Android-версия строится через Capacitor 7: это нативный контейнер для этой же статической веб-оболочки, а не второй клиент с дублирующей логикой. Его постоянный package ID — `ru.phazz.nutriciolog`. Firebase Auth/Firestore и запросы к AI-шлюзу сохраняют текущую модель безопасности: обращаются по HTTPS, пользователь подтверждает сохранение предложенного ИИ блюда, а секреты провайдеров не попадают в APK.

Перед работой нужны Node.js, JDK 21 и Android Studio с Android SDK. `npm run android:sync` собирает временную папку `www/` из статических файлов и синхронизирует её с `android/`; `npm run android:open` открывает проект в Android Studio. Для debug APK запустите в папке `android/` команду `gradlew.bat :app:assembleDebug`; результат — `android/app/build/outputs/apk/debug/app-debug.apk`. В репозиторий добавлен сгенерированный `android/`, но нельзя добавлять signing key, пароли keystore, Firebase service account, `.env` или ключи AI.

Capacitor использует origin `https://localhost`. Он точечно разрешён в исходниках шлюза, но для работы ИИ на устройстве нужно развернуть обновлённый Yandex Cloud Functions ZIP из `yandex/build.py`; Firebase Console также должна содержать `localhost` в Authorized domains. Физическое устройство обязательно для проверки Firebase-входа, камеры, галереи, микрофона и поведения клавиатуры.

Кнопка «Фото» в Android использует нативный Capacitor Camera plugin и открывает заднюю камеру; «Галерея» остаётся системным выбором файлов. При отмене или запрете камеры запись в дневник не создаётся и фото не сохраняется. После изменения веб‑кода или плагинов перед Android‑сборкой запускайте `npm run android:sync`.

## Проверка авторизации при нестабильной сети

`tests/auth-network.cjs` запускает браузерные проверки через Playwright с подменёнными Firebase SDK: задержка восстановления сессии, запрет случайной гостевой записи, гостевой режим, повтор загрузки SDK, задержка/ошибка токена, сохранение полей блюда. Отдельно проверяются тайм-аут кэша оболочки и исключение API/SDK/POST из service worker. Для запуска нужен установленный `playwright` и браузер: `node tests/auth-network.cjs`. Можно задать `PLAYWRIGHT_MODULE` (путь к установленному пакету) и `BROWSER_CHANNEL=msedge` для установленного Edge. Также проверяются кэш профиля между перезагрузками, фоновое обновление, выход/смена аккаунта, поздние ответы, недоступное локальное хранилище, состояние кнопок ИИ и оба выбора источника фото.

Быстрые проверки чистой логики выполняются без браузера: `node --test tests/core.test.mjs` — календарные ключи по локальному времени, цели БЖУ и пересчёт порции.

## Мобильные формы

Поля форм используют шрифт 16 px и сжимаемые колонки, чтобы избежать увеличения при фокусе и выхода полей за границы экрана на iPhone. Длинные формы прокручиваются внутри окна; при появлении клавиатуры высота и положение окна следуют Visual Viewport, с CSS-fallback для браузеров без этого API. Масштабирование жестом остаётся доступным.

Перед ИИ-расчётом обязательно название. Отдельное поле порции необязательно: количество из названия имеет приоритет, когда поле пустое; иначе используется введённая порция. Если количество отсутствует, ИИ предлагает типичную порцию с пометкой об оценке. Пустая порция при сохранении требует расчёта или уточнения, чтобы не записывать нулевой вес.

При открытии ручной формы поля белков, жиров и углеводов не содержат числовых примеров. Они заполняются пользователем или результатом расчёта ИИ.

## Интеграция ИИ с Яндексом

Сайт опубликован в Yandex Object Storage, активный AI_ENDPOINT — Yandex Cloud Functions. Адаптер и сборка ZIP описаны в [инструкции](yandex/README.md). Общие серверные модули сохранены; Firebase ID token передаётся в `X-X20-Authorization`, ключ Blackroute подключается через Lockbox. Фото сжимаются перед отправкой, вызов модели ограничен 40 секундами. Firestore остаётся клиентским и не требует Firebase service account на шлюзе.

Проверка опубликованной интеграции: `node tests/yandex-live.mjs`. Она сверяет endpoint сайта с исходниками, health, CORS и отказ без корректного токена; не вызывает модель и не записывает данные. Реальные вход, текстовый ИИ, фото и сохранение дневника проверены при приёмке v0.2.44. Проверки на физических устройствах и в другой сети без VPN остаются отдельными.

Отложенная операция, отклонённая сервером при повторной отправке (например, из-за прав доступа), остаётся в очереди. Профиль показывает число таких изменений и предупреждение: они сохранены только на устройстве. Следующая попытка после восстановления сети может отправить их после исправления внешней причины. Смена аккаунта останавливает обработку очереди предыдущего UID.

## Проверка правил Firestore

`npm ci`, затем `npm run test:rules` (Node.js 22 и Java 21). Команда запускает локальный эмулятор на 127.0.0.1:8089 с демонстрационным project ID `demo-x20-rules`; рабочий Firebase не используется. Проверяются владелец/чужой UID/гость, запись и удаление всех коллекций, диапазоны БЖУ, идентификаторы, неожиданные поля и структура плана питания. Те же проверки выполняет `.github/workflows/test-firestore.yml`.

При известном офлайне (navigator.onLine=false) запись и удаление сразу сохраняются в локальной очереди UID. Интеграционный tests/firestore-queue.test.cjs проверяет перезапуск и восстановление сети реальным SDK в локальном эмуляторе. При onLine=true операция тоже сохраняется в очередь до обращения к SDK. Подтверждение сервера ожидается до 5 секунд; затем интерфейс сообщает о локальной очереди. Позднее подтверждение удаляет только соответствующую операцию, сохраняя более новое изменение. Потеря транспорта при onLine=true, перезапуск и восстановление соединения проверены реальным SDK.

На главном экране под кнопкой добавления еды расположен короткий совет по сегодняшнему меню. После входа и перезагрузки сравнивается SHA-256 нормализованного меню с последним успешным советом текущего UID/дня. Неизменённое меню не отправляется повторно; изменённое меню получает новый совет с расходом одной попытки квоты. Гость не отправляет меню. Фото, токены и личные сведения профиля в запрос совета не включаются. Совет ничего не записывает в дневник.

Запрос совета ограничен 1000 символами: передаются суммарные калории и БЖУ всех записей и компактный список названий. Сокращение списка явно обозначается; отпечаток для проверки изменений считается отдельно по меню. После ошибки доступна кнопка «Повторить», а восстановление сети также разрешает новую попытку. Карточка оформлена в мятной палитре с меткой «По вашему меню».

При вводе небольшого целого количества для яйца и других счётных продуктов единица переключается до пересчёта. Если выбран продукт базы на граммы и вес штуки неизвестен, завершение ввода запускает AI-оценку веса. После её получения БЖУ считаются из базы; одновременные расчёты для одной формы не дублируются.

Карточка совета использует заголовок 16 px и текст 14 px. Дополнительные действия входа в профиле (создание аккаунта и восстановление пароля) оформлены текстовыми кнопками без фона.

## Оценка расходов ИИ

Блок расходов доступен только выделенному аккаунту, указанному в серверном allowlist. Опубликованный шлюз 0.1.21 проверяет email подписанного Firebase-токена: остальные пользователи получают только `quota`, без `costs`. Веб-клиент v0.2.55 скрывает весь блок. В телефонных исходниках ограничение также добавлено, но требуется новая сборка APK. Учёт запросов и история расходов сохраняются для всех UID.

В профиле добавлены суммы за день, календарную неделю с понедельника и месяц (UTC), в USD. Источник — заданные пользователем 06.10.2026 ориентировочные тарифы за миллион токенов: DeepSeek v3.2 — 0.27 вход / 1.10 выход; Gemini 2.5 Flash — 1.25 вход / 10 выход. Расчёт использует prompt_tokens и completion_tokens из служебного usage Blackroute, включая повтор при неверном формате. Это не счёт провайдера и не стоимость YDB или Cloud Functions. Перед публикацией проверьте версию в `js/core.js` и запускайте deploy из `main`.

Учёт начинается после публикации шлюза 0.1.20. Старые расходы не восстанавливаются, отсутствие записей показывается как «Нет данных». Неизвестный тариф, отсутствие usage или незавершённая запись отмечаются как неполная сумма. Данные изолированы по UID, клиентский кэш не используется. Инструкция включения находится в yandex/README.md. Оплата не подключается.
