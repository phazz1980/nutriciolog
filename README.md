# Мой нутрициолог

Это статический PWA, опубликованный через Cloudflare Pages. ИИ-консультация выполняется Cloudflare Worker: ключ провайдера остаётся в секрете Worker и никогда не загружается в браузер.

## Cloudflare Pages

1. Создайте GitHub-репозиторий и загрузите в его корень `index.html`, `README.md` и папку `worker`.
2. В Cloudflare откройте **Workers & Pages → Create application → Pages → Import an existing Git repository** и выберите репозиторий.
3. Для этого статического проекта задайте ветку `main`, build command `exit 0` и build output directory `.`. Cloudflare выдаст адрес на `pages.dev`.

## Защищённый сервер советов

1. Создайте Worker в Cloudflare и загрузите содержимое папки `worker` (или выполните публикацию через Wrangler у себя).
2. В настройках Worker добавьте секрет с именем `BLACKROUTE_API_KEY`. Его значением служит ключ Blackroute. Не добавляйте его в `index.html`, `wrangler.toml`, GitHub или сообщения.
3. В `worker/src/index.js` указан origin сайта `https://nutriciolog.pages.dev`, поэтому Worker принимает запросы только с этого домена.
4. Worker опубликован по адресу `https://my-nutritionist-advice.340052.workers.dev/api/advice`; это значение уже задано в `index.html`.
5. ИИ доступен любому пользователю, вошедшему через Firebase Authentication. При необходимости ограничение по email можно вернуть отдельной доработкой.

## Ограничения

ИИ отвечает только на общие вопросы о питании и здоровом образе жизни. На вопросы вне этих тем он кратко предложит вернуться к питанию или ЗОЖ. Он не диагностирует заболевания, не назначает лечение и не заменяет врача.

## Firebase: аккаунт и данные

Firebase хранит данные приложения и вход пользователя. Cloudflare Worker остаётся только шлюзом к ИИ; у него нет доступа к Firestore и ему не нужен Firebase service account.

Worker проверяет подпись Firebase ID token через официальный Google JWK endpoint и кэширует публичные ключи по `Cache-Control`. Приватные ключи Firebase или service account ему не передаются.

1. В Firebase Console создайте проект и добавьте Web App. Скопируйте **публичную** конфигурацию Web App в `firebase-client.js`, заменив все `YOUR_...`. Это не секрет и не содержит ключ OpenAI.
2. В **Authentication → Sign-in method → Google** включите провайдер и укажите support email. В **Authorized domains** добавьте `nutriciolog.pages.dev`. Вход через Google нужен для синхронизации и является обязательным для доступа к ИИ.
3. В **Firestore Database** создайте базу и опубликуйте правила из `firestore.rules`. Они разрешают доступ только к документам текущего пользователя: `users/{uid}/...`.
4. Данные организованы так: `users/{uid}/profile/main`, `foodDiary/{дата-uuid}`, `waterLogs/{YYYY-MM-DD}`, `weightEntries/{YYYY-MM-DD}` и личная база продуктов `products/{normalizedName}`. Профиль, вода, ручные блюда, вес и продукты записываются клиентским Firebase SDK после входа; без входа или конфигурации Firebase они безопасно остаются локально в браузере. После входа гостевой профиль не подставляется вместо профиля аккаунта.

На странице «Профиль» можно изменить имя, возраст, рост, текущий и целевой вес, цель и дневную норму. Из Google-аккаунта при входе подставляется только доступное базовое имя; параметры здоровья Google не запрашиваются и заполняются пользователем. На главной странице приветствие меняется по местному времени, а при наличии фотографии Google-аккаунта она отображается вместо стандартной ветки. Сохранение профиля использует тот же Firebase-документ `profile/main` или локальное хранилище в гостевом режиме.

## Как ИИ добавляет блюдо

Если пользователь явно просит добавить блюдо, Worker может вернуть только структурированное предложение: название, калории и приём пищи. Он не выполняет операций с базой. Интерфейс показывает предложение и сохраняет его в дневник только после явного нажатия пользователя «Добавить» — через Firebase client SDK и правила Firestore. Для ручного блюда и предложения ИИ пользователь выбирает дату: сегодня или завтра. Дневник начинается без демонстрационных записей и объединяет продукты одного приёма пищи в общую карточку; сохранённые записи за сегодня загружаются при открытии приложения. Любую отдельную запись, включая перекус, можно удалить кнопкой ×. БЖУ вводятся пользователем для ручного блюда или приходят из подтверждённой карточки продукта ИИ; главная сводка складывает эти значения, а цели БЖУ рассчитывает из дневной калорийности в профиле (30% белки, 30% жиры, 40% углеводы).

В дневнике рядом с названием дня есть кнопка календаря 📅. Через неё можно выбрать любую прошлую дату, сегодня или завтра и просмотреть сохранённые приёмы пищи, порции, БЖУ и сумму калорий прямо в дневнике. Просмотр работает и в Firebase, и в локальном режиме и не изменяет записи выбранной даты.

В ручной форме можно указать название и вес порции, затем нажать «Рассчитать с ИИ». После входа через Google приложение отправляет только эти данные в защищённый Worker и подставляет ориентировочные калории и БЖУ в форму. Блюдо по-прежнему сохраняется только после отдельного нажатия «Сохранить».

Если пользователь запускает такой расчёт без входа, приложение показывает окно с пояснением. Нажатие «Перейти к входу» по явному действию пользователя открывает стандартное окно Google Authentication; при недоступности Firebase пользователь попадает в профиль.

`BLACKROUTE_API_KEY` задаётся только как Cloudflare Worker secret. Его никогда не следует помещать в Firebase, GitHub Pages, исходный код или конфигурацию Firebase.

## Личная база продуктов и карточки ИИ

Когда пользователь просит разобрать или добавить еду по продуктам, ИИ возвращает отдельные предложения с массой, калориями и БЖУ. Интерфейс сверяет название с личной базой текущего пользователя по нормализованному имени и, если запись уже существует, использует сохранённые значения. У каждой карточки есть выбор приёма пищи, даты «Сегодня / Завтра» и отдельная кнопка «Добавить»: только этот клик записывает один продукт в дневник. Новый подтверждённый продукт одновременно сохраняется в `users/{uid}/products/{normalizedName}` для следующих предложений; Worker не читает и не записывает эту базу. Правила Firestore уже разрешают доступ к любым подколлекциям только при совпадении `request.auth.uid` и `userId`, поэтому продукты одного аккаунта не доступны другому.

## Провайдер ИИ

По умолчанию Worker использует Blackroute с моделью `deepseek-v3.2-maas`. Установите переменную Worker `AI_PROVIDER=blackroute`, необязательную переменную `BLACKROUTE_MODEL=deepseek-v3.2-maas` и секрет `BLACKROUTE_API_KEY`. Переключатель моделей в разделе «Совет» доступен только аккаунту `340052@gmail.com`; для всех остальных Worker игнорирует переданную модель и использует стандартную настройку `BLACKROUTE_MODEL`. Для разрешённого аккаунта доступны DeepSeek V3.2, Gemini 3.5 Flash Lite, Grok 4.20 Fast, GPT‑OSS 120B и Qwen3 235B; Worker принимает только этот фиксированный список. Веб-интерфейс получает единый ответ `{ advice, proposedMeal }` и не зависит от конкретной модели или поставщика. Выбранный маршрут пока не анализирует фото блюда: опишите его текстом. Временная строка отладки показывает выбранную модель и HTTP-статус Worker, но не выводит ключи, токены или данные аккаунта.

Выбранные модели Blackroute поддерживают JSON-режим. Worker запрашивает структурированный ответ и дополнительно проверяет его перед передачей приложению; при ошибке Blackroute безопасно сообщает о проблеме с ключом, моделью, лимитом или временной недоступностью без раскрытия секрета.

Если Worker сообщает, что не видит ключ Blackroute, создайте в настройках Worker именно Secret с именем `BLACKROUTE_API_KEY`, а не обычную переменную.

Для безопасной диагностики доступен `GET /api/health`: он показывает версию Worker, активного провайдера, модель и наличие runtime-секрета, но никогда не возвращает сам ключ.

Структура `worker/src/providers/` — точка расширения. Новый адаптер (например, для GigaChat или YandexGPT) должен реализовать `advise(message)` и вернуть тот же объект; его выбор добавляется в `providers/index.js`. Ключ альтернативного провайдера должен храниться только в секрете Worker. Не добавляйте ключи или выбор провайдера в GitHub Pages или Firebase.

Подключайте Blackroute только в соответствии с его условиями использования. Этот проект не реализует обход региональных ограничений.

## Фото блюда

На вкладке «Совет» можно выбрать или снять фото JPEG, PNG или WebP до 4 МБ. Перед отправкой оно видно только локально, его можно удалить. По умолчанию фото передаётся в Worker лишь для одного запроса совета и не сохраняется в Firebase. Оценки калорий и макронутриентов по фото приблизительны и не являются медицинской рекомендацией.

Провайдеры сообщают возможность `supportsVision`. Если выбранный адаптер не поддерживает изображения (например, будущий DeepSeek/Qwen-адаптер без vision), Worker вернёт понятную просьбу описать блюдо текстом. Контракт ответа и подтверждение добавления блюда остаются прежними.

Если позднее потребуется хранить фотографии, используйте Firebase Storage только с путями пользователя, например `users/{uid}/meal-photos/{photoId}`. Добавьте правила Storage, аналогичные Firestore: `request.auth != null && request.auth.uid == userId` для read/write по этому пути, и проверяйте допустимый MIME-тип/размер. Не передавайте изображение от Worker в Storage и не используйте service account: пользовательский Firebase SDK и правила должны оставаться единственным путём записи. Для текущей версии сохранять фото не требуется.

## Голосовой режим

Голосовой режим использует встроенное распознавание речи Web Speech API: он распознаёт русскую речь и вставляет результат в поле вопроса. Нажмите 🎙, чтобы начать; во время записи кнопка становится ■ и отменяет ввод. Озвучивание ответов в браузере отключено. Поддержка, качество распознавания и запрос разрешения к микрофону зависят от браузера и устройства; при недоступности используйте текстовый ввод.

Голосовой режим не требует ключа, нового backend или сохранения аудио. В будущем его можно заменить серверным real-time/audio-streaming адаптером выбранного провайдера, сохранив тот же безопасный пользовательский поток подтверждения блюда. Эта версия не подключает и не развёртывает платный streaming-сервис.

## Установка PWA и офлайн-режим

Для установки нужны HTTPS и опубликованные `manifest.webmanifest`, `service-worker.js`, `pwa.js`, `notifications.js` и папка `icons` рядом с `index.html`. GitHub Pages уже работает по HTTPS и поддерживает относительные пути проекта. На странице профиля появится кнопка установки; если браузер не предоставляет автоматическое приглашение, интерфейс подскажет выбрать «Установить приложение» или «Добавить на главный экран» в меню браузера.

Service Worker кэширует только оболочку приложения. Гостевые локальные функции доступны офлайн, но Firebase-синхронизация, вход и ИИ требуют сети; офлайн-синхронизация облачных данных не заявляется.

## Уведомления

В профиле есть явная кнопка запроса разрешения и отдельные переключатели воды, еды и вечернего веса. Локальная заготовка планирует напоминание средствами браузера; поддержка и фоновая надёжность различаются по платформам. Никакие уведомления не отправляются до согласия пользователя.

Для будущих межустройственных push-уведомлений можно добавить Firebase Cloud Messaging: публичный VAPID key размещается в веб-конфигурации, а отправка выполняется только доверенным сервером с серверными учётными данными. Сейчас FCM, ключи и отправка не настроены; биллинг не включён.

## Мобильные формы

Поля форм используют шрифт 16 px и сжимаемые колонки, чтобы избежать увеличения при фокусе и выхода полей за границы экрана на iPhone. Длинные формы прокручиваются внутри окна; при появлении клавиатуры высота и положение окна следуют Visual Viewport, с CSS-fallback для браузеров без этого API. Масштабирование жестом остаётся доступным.
